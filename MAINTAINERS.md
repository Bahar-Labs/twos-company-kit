# Maintainers

Authorship and maintenance are separate concepts. Authors are the original creators. Maintainers are currently responsible for upkeep. Authors retain attribution even if maintainership changes.

Note: When a second core maintainer joins, enable required code owner review, set required approvals to 1, and turn on dismiss stale approvals.

> **Terminology:** In this document, **contributor** means a person contributing to Two's Company Kit itself. **Collaborator** means a person participating in the shared project being governed with the kit. See the [Terminology](README.md#section-09-terminology) section in the README.

## Section 03. Maintainer status definitions

**Active.** Maintainer responds when relevant maintenance or review is required.

**Maintenance Uncertain.** Two documented maintenance contacts over approximately 30 days receive no response.

**Unmaintained.** No response for approximately 90 days after the first documented maintenance request, or the maintainer explicitly relinquishes responsibility.

**Archived.** Preserved for attribution and history but no longer presented as actively maintained or current.

---

## Section 04. How status changes

Status is determined by response to actual maintenance signals (issues, PRs, review requests), not by commit frequency. Stable content may legitimately require no changes for extended periods. Lack of commits is not the same as lack of maintenance.

## Section 05. When a maintainer is lost

Possible outcomes, in order of preference:

1. The core project adopts the module directly.
2. An approved successor takes over maintainership.
3. The module is archived.

In all cases, original attribution remains. Work you did is work you did. That doesn't change.
